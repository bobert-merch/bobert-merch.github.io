# CLAUDE.md

Maintainer notes for this repo. It's a small, hand-run merch storefront (Bobert × Light Garden VDC) — plain HTML/CSS/JS, no build step, no framework, deployed straight from `main` via GitHub Pages. This file is maintained exclusively by Claude; there's no human dev team reading it, so it's organized for that.

## File organization

```
index.html / feedback.html / about.html   the 3 pages (shop / concepts+feedback form / about)
styles.css                                 ALL css for all 3 pages, one file
site.js                                    ALL js for all 3 pages, one file
assets/                                    images (see "Images" below)
README.md                                  short human-facing blurb
```

**Why one CSS file and one JS file instead of per-page files:** this used to be split (shop.css/feedback.css/about.css, nav.js/cart.js/shop.js/feedback.js). It was merged because the split created cross-file invariants that had to be remembered on every edit — cascade load order, "which file owns this behavior," etc. — and one of them already caused a real bug (a reduced-motion override for `.concept-card` was silently cancelled because a later-loading page file re-declared the same selector). A single file per language is one `Read`/`grep` away from the whole picture, which matters more here than per-page payload size (the whole site is ~35KB of CSS+JS combined). If you're tempted to split it again, don't — fix the specific pain point instead.

**Page-scoping convention:** `styles.css` is loaded by all three pages, so any selector needing different values on different pages must be scoped, not just declared twice — CSS has no file boundary once everything's in one cascade. Each page's `<body>` carries a `page-shop` / `page-feedback` / `page-about` class for exactly this. Right now only the `.hero` family needs it (index.html and feedback.html each have a differently-sized/backgrounded hero section — see `.page-shop .hero` / `.page-feedback .hero` etc. in styles.css). If you add a new selector that needs to differ per page, scope it under the relevant `.page-*` class rather than relying on source order.

**Nav markup is duplicated across all three HTML files on purpose** (not JS-injected). Each page stays fully self-describing when read on its own — opening index.html shows you the whole page, not "load site.js to find out what's actually here." When you change the nav, grep for the section comment (`<!-- NAV`) and edit all three. There is no cart markup to keep in sync anymore — see "Shopify" below.

**site.js structure:** nav/hamburger → scroll lock → Shopify Buy Button bootstrap → swatch selector (banner design preview) → email de-obfuscation → trial modal → concept carousel → one Escape-key dispatcher at the end. Every section only touches elements that exist on the pages that have them (empty `querySelectorAll` loops and `if (!el) return` guards are how it stays safe to load on all three pages) — keep new code following that pattern rather than checking `location.pathname`.

**Accessibility patterns worth reusing, not reinventing:**
- *Trial modal focus management* — opening moves focus to `#trial-modal-close` and traps Tab within the modal (`trapTrialModalFocus`, hardcoded first/last since the modal's two buttons never change), closing restores focus to whatever had it before. If you add another modal/overlay, follow the same shape.
- *Cart status announcements* — `#cart-status` (`.sr-only`, `aria-live="polite"`, duplicated in all 3 pages next to the `site.js` tag) is updated by `announceCart()` in site.js whenever `runCartMutation()` succeeds (banner add/swap/removal). It exists because Shopify's own cart drawer is a cross-origin iframe we can't announce from, and a swatch click has no visual "added" confirmation to hang feedback off of otherwise. If you add another way to mutate the cart, route it through `runCartMutation()` (see "Shopify" below) so this comes for free. `#addon-added-text` (index.html, under the Discord preview card) is the *sighted*-user version of the same idea, set by `setBannerAddedText()` — it doesn't mirror `#cart-status` message-for-message, since it only reflects a swatch press (empty while gated, cleared on background auto-removal, never announces the removal itself).
- `.sr-only` (styles.css) is the shared visually-hidden-but-announced utility class — reuse it for any future hidden label or live region instead of adding a new one.

## Editing products

index.html has in-file HOW-TO comments directly above the product grid and above the add-on card — read those before changing prices, adding a sticker, or adding a banner design. Short version: a sticker is a Shopify product, referenced from markup by one `<div data-shopify-product-id="…"></div>` — no local price/name/description duplication anymore (see "Shopify" below). The add-on card still uses the `.swatch-grid`/`.swatch-btn` picker pattern for its design preview.

The add-on card also has a live preview (`.addon-preview`) mocking a Discord profile popup, so a design can be judged in context instead of as a flat rectangle. `#discord-preview-banner`'s `src` is kept in sync with whichever swatch is `.active` by the swatch click handler in site.js (and set once on load) — no markup changes needed there when adding/removing a design. Swatch buttons have no visible label (the `aria-label` carries the name for screen readers) — the design image fills the button edge-to-edge instead. Banner images are shown at Discord's actual recommended ratio, 5:2 (600×240) — both `.swatch-btn img` and `.discord-card-banner img` use `aspect-ratio: 5/2; object-fit: cover`, so the swatch itself crops the same way the live preview (and Discord itself) does, rather than showing a padded/letterboxed thumbnail. Keep new banner art close to that ratio or it'll crop harder than expected.

Layout: `.addon-card` is a single row (`.addon-main` on the left, `.addon-preview` on the right) that wraps to a stacked column on mobile. `.addon-main` is capped at `flex: 0 1 600px` so it doesn't grow past the swatch grid's natural width; `.addon-preview` uses `flex: 1 1 260px` to claim the rest of the row as its own section and centers the preview card within that whole space (not just within a content-sized box) — if you touch this again, check that the preview isn't just hugging `.addon-main` when the row is wide.

## Images

Product/concept photos are WebP, resized to a 1200px max dimension, quality ~85 (via `sharp`, run through `npx` in a scratch directory — no image-processing deps are installed in the repo itself). Originals are **not** committed; they're kept outside the repo at `../bobert-merch-image-originals/` (sibling to this repo's own folder) in case a design needs to be re-exported. `LG_LOGO.png` stays a PNG on purpose — it's the favicon and `og:image`, and transparency/format compatibility matter more there than file size (it's only 109KB).

## Verify recipe

No test suite; this is a static site, so "verify" means actually rendering it:
```
python -m http.server 8123
```
then drive it with Playwright (not installed in the repo — `npm install playwright` in a scratch dir, `npx playwright install chromium` once per machine). Check: zero console/page errors on all 3 pages, with two known pre-existing exceptions that are not regression signals — the Google Forms iframe on feedback.html throws unrelated font-loading noise, and the Shopify Buy Button SDK (`sdks.shopifycdn.com/buy-button/latest/…`) logs one caught `TypeError: this.fetchData is not a function` at `setupModel` on every page load. That second one was investigated directly (see git history around when Shopify checkout was wired up): it's thrown by the SDK's own internal cart/toggle model setup whenever `ui.createComponent('cart'/'toggle', …)` is called explicitly (which site.js does, so every page gets a shared cart even ones with no product on them) — reproduces identically with a bare-minimum config and no products at all, so it isn't something our options object is doing wrong. It's swallowed internally and doesn't break anything (confirmed end-to-end: add to cart, cross-page cart persistence, and checkout all work). Also check: each product component renders with real Shopify data (title/price/description/image carousel), and the floating cart toggle bubble (fixed to the right edge, mid-page) appears once something's in the cart — **it's intentionally invisible on an empty cart** (`.shopify-buy-frame--toggle.is-sticky` only gets `display:block` once the SDK adds `.is-active`, which happens on the first add-to-cart), so don't mistake "no bubble on a fresh page load" for a bug. `.shopify-buy-frame--toggle` also always renders as *two* DOM elements per page by the SDK's own design (the real `is-sticky` one described above, plus an inert always-`position:static` one sitting at the bottom of the page that's never actually visible/usable) — that's normal, not a sign of double-init; double-init instead looks like two independently fixed-positioned/active toggles, which would mean something pasted a second copy of Shopify's generated loader snippet (see "Shopify" below). Check add-to-cart/qty/remove in Shopify's own cart drawer + cross-page cart persistence, the concept carousel (feedback.html), hamburger + Escape-key behavior, and `prefers-reduced-motion` if you touch any animation/transition — including `html { scroll-behavior }` and any JS `scrollIntoView({ behavior: 'smooth' })` call, since an explicit JS `behavior: 'smooth'` overrides the CSS property and needs its own `matchMedia('(prefers-reduced-motion: reduce)')` check. Also worth a Playwright pass after any layout change: `about.html`'s 2-column grid gets cramped in the ~769–950px range before the main 768px breakpoint kicks in, hence the extra `@media (max-width: 960px)` block just above it in styles.css — if you touch `.about-grid`/`.about-col`, re-check that range rather than assuming 768px alone covers it.

## Shopify

Checkout is real — the Shopify store is `ncpp8a-eh.myshopify.com`, and site.js bootstraps the Buy Button SDK once (client + `ui`), then mounts a `product` component into every `[data-shopify-product-id]` element it finds on the page (currently just the two sticker cards in index.html's `#shop`), plus one shared `cart` and `toggle` component so every page gets the same cart and there's only ever one floating cart tab. Adding/changing a sticker is a Shopify-admin action plus one `<div data-shopify-product-id="…"></div>` in markup — see the HOW-TO comment above the product grid in index.html. `SHOPIFY_STOREFRONT_TOKEN` in site.js is a Storefront API *publishable* token (read-only, checkout-building only) — safe to ship client-side, unrelated to the SSH keys below. It's meant to be public: it's the client-side entry point the Buy Button SDK requires, there is no way to run this storefront without exposing it, and it carries no admin/write scopes. Don't "fix" this by trying to hide it — a public static site has no server to hide it behind, and a Storefront token committed in the open is the intended shape of this integration, not a leak.

**Don't paste a second copy of Shopify's generated Buy Button snippet into markup or site.js** — each one loads the SDK and calls `ShopifyBuy.UI.onReady()` independently, which builds a second `ui` instance and a second floating cart toggle. Add a product by adding a `data-shopify-product-id` element instead; the existing bootstrap picks it up automatically.

`SHOPIFY_THEME` in site.js mirrors the color custom properties in styles.css's `:root` (`--lg-green`, `--surface`, etc.) — Shopify's components render into iframes that never see this page's stylesheet, so `SHOPIFY_UI_OPTIONS` needs real hex values, not `var()` references. If you change the site palette, update both places; nothing enforces they stay in sync.

**Free Discord banner add-on** is product `9694852481267` ("LG Discord Banner", $0.00, see `BANNER_PRODUCT_ID` in site.js). It has four real variants, one per swatch, each with its own dedicated image — titled exactly `Brimstone`/`Chamber`/`Clove`/`Omen`, matching the swatch `data-label` values in index.html's add-on card. `getBannerVariantForLabel()` in site.js matches a swatch click to its variant by title (falling back to whichever variant Shopify lists first if a title doesn't match — a sign the swatch's `data-label` and the variant title have drifted apart, not a supported "no variants yet" mode). Per-variant images mean the correct design now shows as the line-item thumbnail in both Shopify admin's order view and the site's own cart drawer, not just as text. A design also still writes a `Design` **line-item custom attribute** on add/swap — redundant with the variant now, kept as a second, always-visible confirmation of what was picked.

**`hasQualifyingItem()`'s gate is a UX affordance, not a security control — don't rely on it as one.** It's pure client-side JS: a visitor can call `shopifyClient.checkout.addLineItems(...)` directly from devtools and skip it entirely, and more realistically, can add a sticker + banner, reach Shopify's own hosted checkout, then remove the sticker there — `site.js` doesn't run on that origin, so `syncAddonState()`'s poller never sees it and the order completes with just the free banner. This is accepted, not an oversight: the banner is a $0.00 digital line, so the cost of a bypass is fulfillment noise (an order with no paid item), not lost money, and a server-side fix (a Shopify Function validating cart contents) would be disproportionate to that. If the add-on ever carries real cost or inventory, this needs real enforcement before that happens. Relatedly, `addOrSwapBannerDesign()` writes the matched **variant's own title** (`variant.title`, called `safeLabel` in the code) to the `Design` attribute rather than the caller-supplied label — the function is reachable from the console, and that attribute persists into Shopify admin/emails/packing slips, so this keeps arbitrary console-typed strings out of real orders even though the gate above doesn't stop the order itself from happening.

Gating is unchanged from the original design: `hasQualifyingItem()` requires a non-banner line already in the cart before a swatch click adds anything — no automatic retry, same as before. `.addon-hint`'s copy ("Add a sticker to your cart first…") is a **permanent fixture in the markup, not toggled by eligibility** — it used to hide once `hasQualifyingItem()` became true, but for a returning visitor whose cart already qualified that meant it flashed visible then vanished a couple seconds later (once the SDK loaded), which read as a bug rather than correct behavior. It's always-on now, at the cost of being slightly stale once you already have the banner — a deliberate trade, not an oversight, so don't reintroduce the toggle without solving the flash first. What's different from a typical Shopify integration: the Buy Button SDK doesn't expose a "cart changed" event (its own drawer's remove/qty buttons live inside an iframe we don't control), so there's no way to react instantly if a paid item gets removed *from the cart drawer itself*. `syncAddonState()` polls every ~3s instead (skipped while `document.hidden`, so a backgrounded tab isn't polling for nothing) and prunes the banner line if no paid item remains — a deliberate, documented trade-off (polling delay) rather than the old local-cart's synchronous enforcement.

Cart mutations for the banner use `client.checkout.addLineItems`/`updateLineItems`/`removeLineItems` (not the simpler `cart.addVariantToCart()` the SDK exposes, which doesn't support custom attributes) — but **never call those directly; always queue them through `runCartMutation()`**. That wrapper is a single serialized promise chain (`cartMutationQueue`) that exists for two reasons: (1) one shared `.catch()`, so a network blip or expired checkout doesn't become an unhandled rejection that leaves the drawer showing a stale cart, and (2) ordering — a burst of swatch clicks fires overlapping requests against the same checkout id with no inherent ordering, so without the queue the *slowest* response wins rather than the visitor's most recent click. Each queued task re-reads `hasQualifyingItem()`/`findBannerLineItem()` when it actually runs rather than closing over state computed when it was queued, which is also what stops `syncAddonState()`'s poll from re-issuing a removal for a line an earlier queued task is already removing. On success, `runCartMutation()` calls `afterCartMutation()`, which replays the same view-refresh steps `addVariantToCart` runs internally (calling `client.checkout.*` doesn't update the visible cart/toggle on its own) and fires `announceCart()`. `runCartMutation()` also takes an optional third `visibleText` argument that updates `#addon-added-text` (the sighted-user "[design] added to cart" line under the Discord preview) — pass a string to set it, `''` to clear it, or omit the argument to leave it alone. `addOrSwapBannerDesign()` passes `` `${safeLabel} banner added to cart` `` (see the `safeLabel`/variant-title note above); `syncAddonState()`'s auto-removal passes `''` so a stale "added to cart" message doesn't linger once the banner's actually gone, without implying the removal was itself a swatch press. Earlier versions of this had a swatch click pop the cart drawer open (mirroring what a sticker's own Add to cart button does via `cart.addVariantToCart()`) — that was deliberately replaced with this text instead, so don't reintroduce `shopifyCart.open()` here without checking that's actually wanted again.

One SDK quirk worth knowing if you touch this: `client.product.fetch(id)` needs the **base64-encoded** GraphQL id (`btoa('gid://shopify/Product/' + id)`), not the plain numeric id `ui.createComponent('product', {id, ...})` accepts elsewhere — found by trial, not documented anywhere obvious.

## AI/crawler accessibility

`robots.txt` and `llms.txt` at the repo root, plus `sitemap.xml` (3 URLs — the site is just 3 pages). All plain static files, no server config needed since this is GitHub Pages. index.html also has a `FAQPage` JSON-LD block in `<head>`, generated from the FAQ `<details>`/`<summary>` content in the `#faq` section — **if you edit the FAQ copy, update the JSON-LD to match** (same questions/answers, verbatim); nothing enforces that they stay in sync, it's just a convention. No `Product` schema has been added yet — it was withheld while checkout was fake (adding price/availability markup would have overclaimed purchasability), but checkout is real now (see "Shopify" above), so it'd be legitimate to add as a follow-up.
